## 实现方案

### 背景与目标

已核实的现状：

- `EditorRegistry` 在内存中保存编辑内容，已有保存冲突检测，但未保存内容不跨重启恢复。
- 编辑器条目以布局窗格 ID 为键；同一项目内同一路径（不区分大小写）只打开一个编辑器。工作区按需挂载，只有访问过的项目才会根据布局创建编辑器条目。
- 文件监听采用有界队列和事件合并。监听回调对每个原始事件都先将索引标记为失效，然后才过滤 `.git` 与 `.orbyte-*.tmp` 路径，因此 Git 内部变化和编辑器原子保存产生的临时文件也会使下次搜索完整重建文件名索引。
- 文件名索引最多收录 100,000 个文件，超出时截断并标记为不完整。
- 已有前端逻辑测试、Rust PTY 测试和发布检查脚本，原生安装验收结果尚未在检查表中记录。这不代表实际未执行过验收。

交付目标：

1. 异常退出后，可以恢复最近一次成功落盘的草稿。
2. 关键桌面交互具备明确、可重复执行的验收步骤。
3. 减少与文件名搜索无关的索引重建，并用数据验证效果。

### 方案概述

先建立验收与性能基线，再实现草稿持久化、编辑器接入和恢复交互；文件索引优化以基线为依据独立推进。最终通过安装版验收，更新使用说明和发布记录。

每一步独立提交、独立验证。终端历史搜索、通知跳转、项目启动配置、多终端资源占用基线列入后续迭代，分别独立交付，避免扩大本轮改动范围。

### 详细设计

#### 编辑器草稿恢复

使用现有 SQLite 存储能力，新增独立草稿表，通过新迁移追加，不修改历史迁移。

草稿记录包含：项目 ID、相对路径、编辑内容、原始磁盘基线版本、编码信息、修订号和更新时间。

- 项目 ID 外键关联 `t_project`，`ON DELETE CASCADE`，删除项目时一并删除草稿。
- 相对路径使用 `COLLATE NOCASE`，与编辑器和布局的路径比较规则一致；项目 ID 与路径组成唯一键。
- 正文上限与 `MAX_FILE_BYTES`（5MB）一致，超出时不写入并提示。
- 草稿表的约束冲突使用独立错误信息，不复用 `db_error` 中针对项目与分组的提示。

处理流程：

1. 编辑发生后去抖写入草稿，持续输入时设置最长刷新间隔，避免一直不落盘；内容与上次成功写入相同时跳过。
2. 每份文档的草稿操作串行执行，防止旧写入覆盖新内容。
3. 文件保存成功后，仅清理对应修订号的草稿；保存期间的新输入继续保留。
4. 撤销回磁盘基线（不再处于未保存状态）时清理草稿。
5. 重命名文件或目录时，在同一事务中迁移草稿路径；目录按前缀迁移，与 `EditorRegistry.rename` 规则一致。
6. 恢复只更新编辑缓冲区；磁盘内容变化时提示冲突，保存继续使用现有版本校验。
7. 文件删除、项目路径不可访问时，保留恢复内容并允许复制。
8. 项目根路径被修改后，原草稿不自动套用到新根目录，在恢复入口中标记为“项目路径已变更”，由用户查看、复制或丢弃。

放弃修改的入口及处理（对应 C03）：

| 入口 | 位置 | 草稿处理 |
| --- | --- | --- |
| 关闭窗格或 Tab 时“放弃修改并关闭” | `WorkspaceView.confirmAction(false)` | 清理所关闭编辑器的草稿 |
| 项目级“放弃修改并继续” | `WorkspaceDeck.resolveDiscard` | 清理该项目编辑器的草稿 |
| 退出时“不保存退出” | `App.resolveClose('discard')` | 清理全部已打开编辑器的草稿 |
| “放弃修改并重新打开”、冲突时“重新加载” | `EditorPane` | 重新加载成功后清理该编辑器草稿 |
| 任一确认框选择“取消” | 上述各处 | 保留草稿 |
| 异常退出、强制结束进程 | — | 保留草稿 |

恢复入口分两层：

- **编辑器内恢复**：编辑器条目完成磁盘读取后，若匹配到同一项目和路径的草稿，在编辑器内提示恢复或丢弃。顺序固定为“读取磁盘、应用草稿、开启草稿同步”，避免初始化内容覆盖草稿。
- **启动全局提示**：启动时查询全部草稿，若存在则提示并列出项目、路径与更新时间，覆盖尚未访问的项目以及布局中已无对应窗格的孤儿草稿，支持打开、复制和丢弃。

草稿正文不进入诊断日志。现有 `diagnostics.ts` 只记录 ID 和错误类别；草稿写入命令频率高，需加入 `quietCommands`，避免日志被刷屏。首版恢复文本内容和必要元数据，不恢复撤销历史。草稿是独立恢复副本，不自动写回源文件。

#### 文件索引优化

先记录基线，再修改失效机制。索引失效判断移到事件分类之后，不再在监听回调中对每个原始事件直接标记失效。

结构变化（触发索引失效）：

- 创建、删除、重命名事件，以及无法可靠分类的事件。
- 忽略规则文件变化：任意层级的 `.gitignore`、`.ignore`，以及 `.git/info/exclude`。

非结构变化（只通知编辑器与文件树，不触发索引失效）：

- 文件内容或元数据修改。
- `.git` 内部变化，`.git/info/exclude` 除外；Git 状态刷新维持独立机制。
- `.orbyte-*.tmp` 临时文件的创建、删除和重命名。
- 重命名或创建的目标文件已在当前索引中（原子保存覆盖已有文件），通过索引路径集合判断。

兜底与保持项：

- 队列溢出、监听异常、`need_rescan` 继续触发完整重建。
- 构建前先将失效标记清零，构建期间的新事件会重新置位。现有实现已满足，保持不变并补充测试。

已知限制：worktree 项目中 `.git` 是文件，exclude 规则位于主仓库 gitdir；全局 `core.excludesFile` 同样在项目目录之外。这两类规则变化不在监听范围内，需重新打开项目或等待其他结构变化后生效，在使用说明中注明。

本轮保留完整重建方案，通过减少无效重建降低成本；增量索引另行迭代。

**验证方式**：完整测试与构建检查通过，文档中的功能描述与安装版行为一致。

### 风险与权衡

- **草稿仍有时间窗口**：强退可能丢失尚未落盘的最后一段输入，界面和文档应明确这一边界。
- **本地内容留存增加**：草稿可能包含敏感文本，必须提供明确的丢弃入口，并排除日志正文记录。
- **放弃即清理**：用户选择“不保存退出”后无法再找回内容，这与界面文案一致；如需保留，应选择取消。
- **保存与清理存在竞争**：通过修订号、串行执行和条件删除保护新内容；应用重启后同样不得复用会与旧记录冲突的修订标识。
- **单连接写入排队**：数据库只有一个写连接，大草稿频繁写入会延迟布局和设置保存；通过去抖、相同内容跳过和大小上限控制。
- **事件分类可能遗漏变化**：不明确的事件保持完整重建兜底，以正确性优先。
- **原生验收需要交互环境**：自动检查通过不能替代安装版输入法、通知和进程清理验证。
- **数据库变更需兼容旧数据**：仅追加迁移，验证已有数据库升级；不通过修改历史校验和规避新迁移。

### 验收标准

- 异常退出后能找回最近一次成功落盘的草稿，包括未访问项目和孤儿草稿。
- 恢复、保存、重命名、丢弃和取消关闭之间无内容误覆盖或误清理。
- 磁盘变化、文件缺失、项目不可访问和项目路径变更时，恢复内容仍可查看或复制；不自动覆盖源文件。
- 文件名搜索在结构和忽略规则变化后正确更新；内容修改、编辑器保存和 `.git` 内部变化不造成重建。
- 固定样本有优化前后的性能数据、测量方法和环境说明。
- 关键安装版场景具有可追溯的执行结果。
- 完整验证通过，已有文件冲突保护和终端生命周期行为无回归。
